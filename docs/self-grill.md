# 自行 grill：分支记录（v0.1）

按 grill-me 的 self-grill 模式逐分支收口；每条给出结论、依据与当前状态。

## 1. 范围与形态

- 问题：这是新项目、新子系统，还是小改动？
  结论：architectural（新项目，仓库里没有任何既有流程可改）。状态：evidence-resolved。
- 问题：是否要先出设计稿再实现？
  结论：否。用户明确说“自行 grill，给我做出来第一版”，已授权直接实现；因此把设计决策写进本文件与
  README，不额外停在设计审批门。状态：evidence-resolved（用户原话）。
- 问题：前后端形态？
  结论：静态 SPA（Vite + React 19 + TS），`base: './'` + HashRouter，dist 可丢到任意静态托管；
  第一版不做服务端。理由：先证明展馆本身的交互与视觉，再谈写入链路。状态：reversible-default。

## 2. 数据真实性（最高风险分支）

- 问题：示例数据会不会被误认为真实作者的作品？
  结论：不会。数据模型里 `provenance.source` 只有 seed 与 github，卡片与详情页按来源渲染
  「示例」/「GitHub 实时」标记，详情页有独立「数据说明」段落；seed.ts 每条都带
  note“演示示例数据…未指向真实作者的作品”。状态：evidence-resolved（validateProjects.test.ts
  断言 seed 整体通过校验）。
- 问题：GitHub 条目能不能编造创作故事？
  结论：不能。story 字段保存仓库自述原文并加前缀，prompt/iterations 留空，页面相应区块不渲染。
  状态：evidence-resolved（scripts/fetch-github.mjs 的 toProject()）。
- 问题：搜索结果混进 awesome-list / 教程 / 基建仓库怎么办？
  结论：四重过滤 —— STOP_TOPICS 标签黑名单、LISTY/TOOLING 描述正则、VIBE_SIGNAL（vibecoding 关联
  必须能从仓库自身证据看出）、作品特征（有 demo 链接或 stars <= 1200）。状态：evidence-resolved
  （两轮真实抓取对比：24 条工具/合集 -> 14 条更像作品）。
- 问题：抓取失败会不会清空已有快照？
  结论：不会。零结果时只以非零退出码退出，不写文件。状态：reversible-default。

## 3. 交互与视觉

- 问题：什么算“交互高级”？
  结论：⌘K 命令面板（键盘选择 + 高亮 + 滚动跟随）、URL 化筛选状态、FLIP 布局动画、指针驱动 3D
  倾斜与光斑、程序化封面、主题切换（View Transition）。状态：evidence-resolved
  （verify:ui 逐项点击断言 + 截图）。
- 问题：动效会不会影响可访问性？
  结论：prefers-reduced-motion: reduce 时关闭倾斜/漂移/跑马灯/过渡；交互元素是原生 button/link，
  带 aria-pressed、aria-live、可见焦点环与跳过链接。状态：evidence-resolved（verify:ui 的
  reduced-motion 与键盘检查）。
- 问题：中文字体不能联网加载怎么办？
  结论：只用系统字体栈，封面用程序化 SVG/CSS 生成，不依赖任何 CDN 或第三方图片。
  状态：evidence-resolved。
- 问题：同分类的作品封面会不会长得一样？
  结论：第一版会（同类同色相）。已加按 slug 哈希的色相抖动，同分类也不同门面。
  状态：evidence-resolved。

## 6. 优化轮（“优化”指令，先量后改）

原则：先用 `scripts/measure.mjs` 采基线，再改，再用同一脚本复测；量不到差异的改动不当成果汇报。

- 问题：优化什么？
  结论：只锁定“可测量”的四类 —— 首屏体积、DOM 节点数、两个真实缺陷（锚点被顶栏遮挡、命令面板焦点）、
  搜索质量与可访问性；不做没有度量方式的“感觉更快”。状态：evidence-resolved。
- 问题：要不要为了减包把动画库整个去掉？
  结论：去。它的能力可以被更轻的手段覆盖：入场动画用 CSS keyframes（`--i` 错峰）、倾斜与光斑在 DOM 上
  写 CSS 变量（rAF 合并，每帧最多一次写）、筛选切换用原生 View Transitions。实测首屏 JS
  463,011 → 324,116 字节，DOM 2,026 → 1,112。代价：失去逐卡 FLIP 布局动画，换成整页交叉淡入
  （Chromium 支持；不支持时直接切换，不报错）。状态：evidence-resolved，可回滚（父提交 da9f610）。
- 问题：屏外渲染跳过（content-visibility）有效吗？
  结论：本机 34 张卡时强制布局中位数 0.1ms → 0.2ms，**测不出差异**，因此按“为更大目录预留的防御性改动”
  记录，不作为性能成果。状态：evidence-resolved（含负结果）。
- 问题：锚点缺陷是什么？
  结论：HashRouter 下英雄区 `href="#hall"` 会被当成路由跳转，点“进入展馆”实际落到兜底页 /hall。
  现在拦下默认行为改页内滚动，并给 section 加 `scroll-margin-top`，标题不再被 sticky header 遮住。
  状态：evidence-resolved（组件测试 RED→GREEN + 浏览器几何断言 132px > 67px）。
- 问题：命令面板的键盘体验如何？
  结论：加焦点陷阱（Tab 在面板内循环）、关闭后焦点还给打开它的元素、触发按钮 `aria-expanded`。
  注意 `autoFocus` 会在提交阶段先抢焦点导致“记错来源”，因此改成先记录再显式聚焦。
  状态：evidence-resolved（单测 + 浏览器内 20 次 Tab 断言）。
- 问题：搜索只是子串匹配，够用吗？
  结论：不够。加相关性打分（标题 > 标签/技术栈/作者 > 简介 > 故事，标题前缀加权最高），并列时沿用用户
  选择的排序，并在结果里高亮命中词。状态：evidence-resolved。
- 问题：精选位是不是被同类霸榜？
  结论：会。改成 `pickFeatured` 先每分类各占一席再按热度补齐；现在精选四条分属四个分类。状态：evidence-resolved。
- 问题：真实无障碍状况如何？
  结论：接入 axe-core（wcag2a/2aa/21a/21aa）在深色与浅色各扫一遍。第一轮扫出两处真实对比度不足
  （英雄区统计标签、浅色工具栏与页脚），已调整设计令牌；现在深浅色均 0 条严重问题。状态：evidence-resolved。
- 问题：优化会不会改坏既有行为？
  结论：不会。50/50 单元与组件测试、33/33 浏览器运行时检查、零 console error，提交前仍跑
  `npm run build`（tsc + vite）并复核截图。状态：evidence-resolved。
- 问题：还有没测到的地方？
  结论：首次内容渲染没有优化前的基线数据，因此不声称渲染提速；移动端只验了渲染与卡片存在性，
  没做真机手势/滚动性能测试；GitHub 条目的分类仍是启发式。状态：deferred（不阻塞）。

## 7. 愿望墙与接单（本轮）

- 问题：“加一个想要的愿望描述，接单”是给展馆加什么？
  结论：加需求侧 —— 一面愿望墙：贴「我想要一个能…的东西」→ 别人「我来接单」→ 做完关联展品变「已交付」。
  与大厅（作品侧）互为两端，详情页不新增冗余入口。状态：evidence-resolved（用户原话）。
- 问题：没有后端，怎样才不算骗人？
  结论：三个必须：① 顶部明文写「只存在这台浏览器、别人看不到」；② 卡片按来源标「本机 / 示例」；
  ③ 提供「导出 JSON」把本机内容交给维护者。同时存储损坏时回落到空改动、绝不白屏。
  状态：evidence-resolved（界面文案 + `wishBoard.test.ts` 的损坏存储用例）。
- 问题：状态机怎么定才不会互相踩？
  结论：只允许 待接单 →(接单)→ 已接单 →(交付)→ 已交付；重复接单、接已交付、非接单人交付、
  交付缺作品与链接，四种非法转移各返回明确原因码并转成中文提示。状态：evidence-resolved
  （`wishes.test.ts` 16 项 + 页面 8 项）。
- 问题：接单/交付用弹窗还是就地展开？
  结论：就地展开。弹窗会丢掉“这是哪条愿望、谁接的”上下文；就地展开同时让键盘顺序自然、
  少一层焦点管理。状态：evidence-resolved（截图 + 40 项运行时检查）。
- 问题：本地贴的愿望能不能被接单？
  结论：第一版**不能** —— `applyPatch` 只把接单/交付/想要叠加到种子愿望，忽略 `patch.created`。
  浏览器端到端检查（贴 → 接单 → 交付）把它暴露出来，已改为种子与本机愿望走同一条叠加路径，
  并补了两条回归测试。状态：evidence-resolved（RED→GREEN）。
- 问题：还有什么没做到？
  结论：没有身份验证，接单人是自证；没有多人同步（本机存储）；愿望不能删除/编辑；
  愿望与展品的关联是单向的（展品详情页还没反查“来自哪条愿望”）。状态：deferred（不阻塞）。

## 8. 升星榜 + 文案瘦身（本轮）

- 问题：升星榜靠什么数据才不算编？
  结论：GitHub API 只给当前星标，不给历史。所以由抓取脚本维护 `github-history.json`（每次追加一条
  `{时间, 仓库→星标}`，上限 180 条）；窗口内不足两次快照时，增量列显示 `—`、增量榜按钮禁用并写明原因。
  另外提供两条立刻可算的真实榜：日均星标（创建至今）与总星标。状态：evidence-resolved。
- 问题：三条榜如何避免互相冒充？
  结论：增量榜（真实差值）/ 增速榜（日均，来自 created_at）/ 存量榜（当前星标）分列三处，
  界面上写明各自依据；默认自动选择“有意义的那个”——没有正增量时自动落到增速榜，
  避免把一个全是 0 的榜当结果展示。状态：evidence-resolved。
- 问题：“按日、月等分统计时间”怎么落地？
  结论：窗口 日 / 周 / 月 / 全部，相对最新一次快照计算；窗口内快照数单独显示，
  让用户知道当前窗口有几个数据点。状态：evidence-resolved（页面测试含窗口切换）。
- 问题：“分类，skill，软件啥的”怎么分？
  结论：技能包 / 软件应用 / 库与框架 / 清单合集 / 其它，按名称+简介+topics 的启发式规则判定，
  先判清单再判技能、软件、库。真实数据上从「其它 4」修正为「软件应用 9 / 其它 1」——
  开发工具类（workspace / 终端 / 驾驶舱）归到软件应用。状态：evidence-resolved（RED→GREEN）。
- 问题：脚本里踩了什么坑？
  结论：第一版先写新的 live 文件、再去读“旧 live 快照”来建立历史，结果读到的是刚写的新文件，
  快照历史只剩 1 条（等于没有增量）。改成进入主流程时先读上一份 live，再写新文件并追加历史。
  状态：evidence-resolved（历史文件里现在有 2 条真实快照）。
- 问题：“那些没用的字”删哪些？
  结论：只删界面上的装饰性说明文字：首页英雄区长段简介压缩成一句、示例/实时提示压成一行、
  大厅与愿望墙的提示压缩、关于页四张卡各压成一行、提交页说明压成一句、搜索框去掉括号里的快捷键字样
  （改挂 title）。保留：示例/实时/本机来源标记、快照与数据来源说明、状态机规则——这些是可信度的一部分。状态：evidence-resolved。
- 问题：还有什么没做？
  结论：没有星标随时间变化的曲线图；没有按作者聚合的榜；“删除／编辑”愿望的能力仍缺；
  真实涨势需要用户定期跑抓取脚本（本机没有调度器）。状态：deferred（不阻塞）。

## 9. 论坛 / 用户信息 / 登陆 / 资金（本轮）

- 问题：“登陆”要不要做一个登录框？
  结论：**不做假登录**。没有服务端就没有验证、没有会话、没有凭据保护，做一个能点进去的登录框
  等于告诉用户“你已登录”，这是安全反模式。改为**本机身份**（署名），界面三处写明：不是账号、
  没有密码、没有验证、不上传。状态：evidence-resolved（页面文案 + 测试断言“不是账号”可见）。
- 问题：“资金”要不要做钱包或余额？
  结论：**不做假资金**。做余额/充值/提现必须承接真实资金流（主体、资质、渠道、托管、风控、对账、合规）。
  改为**意向悬赏**：愿望上可标金额与说明，只展示；并在表单旁与卡片上写明“不收款、不支付、不托管”。
  真实的接入条件写进 `docs/money-and-auth.md`。状态：evidence-resolved，`资金 = blocked`。
- 问题：论坛做成真的还是单机？
  结论：单机版（复用它已经验证过的“本机存储 + 叠加表 + 导出”模式）。真相是：真多人论坛必须有后端；
  单机版的价值是把数据模型、分类与交互先钉死，并给出一条可提交的导出通道。界面必须直说“别人看不到”。
  状态：evidence-resolved。
- 问题：三个功能要不要各写一套存储？
  结论：不要。身份、帖子、愿望都走同一套模式：纯函数领域层 + 叠加表 + localStorage + 导出 JSON + 重置。
  好处是行为一致、可测、坏数据可回落（三处都有“存储损坏不崩溃”的用例）。状态：evidence-resolved。
- 问题：身份怎么和已有功能打通？
  结论：愿望的署名/账号、接单署名、发帖作者都默认取本机身份；没身份时论坛发帖按钮禁用并指向 `/#/me`。
  顶栏加了身份入口（头像色 + 昵称），个人主页聚合我的愿望/接单/帖子/回复。状态：evidence-resolved。
- 问题：踩到的两个坑？
  结论：① 论坛的“单机版”提示被 `<strong>` 拆成了多个文本节点，测试用文本匹配直接失败——说明文案结构
  会影响可达性测试，改为单节点表达；② 测试里直接调用 store（没包 `act`）导致页面没重渲染，
  断言读到 0——这是测试写法问题，用 `act` 包住而不是放宽断言。状态：evidence-resolved。
- 问题：还没做 / 做不了的？
  结论：真实登录（blocked：缺服务端与 OAuth 凭据）、真实资金（blocked：缺主体、资质与法务）、
  论坛审核与反垃圾、帖子编辑与删除、跨设备同步。本机身份对 handle 没有所有权校验——这是没有后端的固有限制。
  状态：blocked（前两项）/ deferred（其余）。

## 10. 第二轮优化（先量后改，含测量口径纠错）

- 问题：这轮优化什么？
  结论：先用只读检查找出「有证据的缺陷」，而不是凭感觉调参。三条新检查在改之前全部失败：
  移动端导航不可达（0 个可见导航项）、⌘K 搜不到页面（0 条匹配）、未知路径落到展品的「没有这扇门」。
  另外读代码时发现第四个缺陷：只填昵称没填账号时，「我的愿望 / 我的帖子」恒为 0。状态：evidence-resolved。
- 问题：移动端为什么点不到别的页面？
  结论：`.site-nav` 在 ≤820px 被 `display: none`，而且没有任何替代入口（⌘K 只搜展品）。
  改成换行成第二排 + 横向滚动；同时把 ⌘K 变成全站跳转，作为移动端的第二条通路。状态：evidence-resolved
  （浏览器实测：6 个可见导航项）。
- 问题：⌘K 怎么扩展到全站？
  结论：把面板从「展品列表」抽象成通用条目层 `paletteItems`（页面 / 展品 / 愿望 / 帖子，带 id 与排序权重），
  标题命中优先、其余按热度并列；选中愿望或帖子会跳到 `?focus=<slug>` 并高亮那一条。
  副作用：顺序变了——「看板」的第一条从副标题命中的睡眠仪表盘变成标题命中的霓虹看板，这是设计意图，测试随之更新。
  状态：evidence-resolved（单测 + 浏览器实测 `#/wishes?focus=highlight-cards` 且高亮 1 条）。
- 问题：身份只填昵称时统计为什么是 0？
  结论：统计函数只按 handle 匹配，而 handle 允许留空。改成 handle **或**昵称任一匹配；
  `countMyContributions` 也加上昵称参数。状态：evidence-resolved（RED→GREEN）。
- 问题：身份是后来才设置的，表单还带旧值怎么办？
  结论：愿望表单与接单表单在身份变化时补空字段（`current || profile.x`），不覆盖用户已输入的内容。
  状态：evidence-resolved（单测：后设置身份 → 打开表单 → 署名已填）。
- 问题：这轮改动有没有把首屏包弄大？
  结论：一开始变大了（index 65 → 87.9 kB），因为把两个存储层与种子数据拉进了初始包。改成

## 14. 第三轮优化：长页成本 + 探针全路由覆盖（本轮）

- 问题：这轮优化谁？
  结论：优化**上一轮自己引入的成本**——一行一个案例让展馆变成约 7,500px 的长页，而首屏仍一次性渲染
  30 张卡（约 540 个节点）。状态：evidence-resolved。
- 问题：怎么解？分页还是虚拟列表？
  结论：**渐进渲染**（首屏 12 条 + 「再看 N 条」）。虚拟列表对 30-60 条是过度设计，而分页会打断
  浏览节奏；渐进渲染只需一个 visibleCount 与一个 useEffect（筛选/排序/版式变化时回到第一批）。
  状态：evidence-resolved（单测 3 项：首批只渲染 12、点一次追加、改筛选回到首批）。
- 问题：长页还缺什么？
  结论：缺两个导航手段：**筛选工具栏吸顶**（滚到深处不用滚回顶部改筛选）与**右下角「回到顶部」**
  （滚过 15% 才出现）。状态：evidence-resolved（浏览器实测：滚动后 toolbar 顶部 62px、顶栏底部 67px；
  回到顶部点击后 scrollY=0）。
- 问题：效果有多少？
  结论：**DOM 节点 1,139 → 600（−47%）**、首屏卡片 30 → 12、FCP 536 → 424 ms（同机同脚本）。
  首屏 JS 338,281 → 339,095 字节（+814 字节，增量来自分页与回顶逻辑）。状态：evidence-resolved。
- 问题：探针覆盖够吗？
  结论：不够。之前 target-size / 视口压力只跑首页，而 `ui-verification` 要求这三条便宜探针跑**每个路由**。
  现在跑 6 个路由（展馆 / 升星榜 / 愿望墙 / 论坛 / 我的 / 展品详情）× 360 与 1280 两个宽度。
  状态：evidence-resolved。
- 问题：扩了覆盖之后发现了什么？
  结论：立刻抓到一处真缺陷——`/wishes` 在 360px 下愿望卡宽 355px、右边界 378（溢出 18px），
  根因是 `grid-template-columns: repeat(auto-fill, minmax(360px, 1fr))` 的固定下限比可用宽度还大。
  修法：`minmax(min(360px, 100%), 1fr)`；顺手把大厅网格的 `minmax(320px, …)` 也一起防住。
  状态：evidence-resolved（clearance re-run：6 路由 × 2 宽度共 12 次测量全部无溢出）。
- 问题：还有没测到的？
  结论：**320px** 没测（探针只到 360）；触屏 44px 建议值只记录不判失败；虚拟列表/分页未做
  ——若展品数涨到几百条，渐进渲染需要配合虚拟化。状态：deferred。

## 16. 个人中心补强 + 虚拟积分/徽章商店（本轮）

- 问题：“个人中心做好了吗？”——先核对事实再回答。

  结论：做**虚拟积分 + 馆内徽章商店**：积分只能靠行为获得（贴愿望 +5 / 发帖 +10 / 回帖 +3 / 评论 +5 /

  状态：evidence-resolved。

  结论：三处写死：个人中心顶部说明、`CREDITS_DISCLAIMER` 常量、导出载荷里的 `disclaimer` 字段
  （含“虚拟”“不能充值、不能提现、没有真实价值”）；并保留 `docs/money-and-auth.md` 的 blocked 结论。
  状态：evidence-resolved（浏览器实测页面确实显示该文案）。
- 问题：积分会不会是凭空写死的数字？
  结论：不是——它是**流水求和**，每笔都有 reason、note、日期与稳定 id，可导出审计；
  端到端验证时余额恰好是 120+5+5+10+3+8+20 = **171**，与规则表逐项对上。
  状态：evidence-resolved。
- 问题：这轮的“优化”指什么？
  结论：两件事：① 把积分反馈放到用户已经在看的地方（侧边栏身份卡、愿望墙底栏、评论表单旁的“每条 +5 积分”），

  状态：evidence-resolved（构建产物仍为 react/router/index 三块 + 各页懒加载）。
- 问题：还有什么没做？
  结论：积分没有有效期与每日上限（理论上可以刷）；徽章不能展示在卡片/帖子上（只是“已拥有”）；
  没有排行榜；真实支付仍 blocked。状态：deferred。
